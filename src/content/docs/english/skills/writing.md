## 写之前先确定读者要做什么

报告结果、请求帮助、提出安排、解释风险，结构各有重点。先写一句核心目的，再补读者作决定所需的信息。不要为了显得正式把每句都写成长句。

## 一封清楚的请求邮件

**Subject: Review request for the access policy**

Hi Maya,

I've updated the access policy for the demo. Could you review the changes before Thursday afternoon? I'm especially interested in whether the resource checks cover the cases we discussed.

The test results are included in the document. Please let me know if you need more context.

Thanks,
Haijiang

这是一份模拟邮件。真实发送时，更新、测试、附件与截止时间都必须与事实一致。

## 段落按作用组织

第一段给背景与请求；第二段提供材料和补充途径。若有多个独立问题，可以列出明确问题，而不是把所有内容埋进长段落。

**错误方向：** “I have some questions about many things and maybe you can help…” 太模糊。

**更具体：** “Could you confirm whether the policy applies to archived files?” 问题范围与预期动作都清楚。

## 四轮修改

| 轮次 | 检查 |
| --- | --- |
| 内容 | 读者知道目的、事实和下一步吗？ |
| 逻辑 | 原因、结果、对比与限制对应吗？ |
| 句法 | 主谓、时态、冠词、从句结构是否准确？ |
| 表达 | 搭配自然吗？有无多余或含糊措辞？ |

不要只替换“高级词”，却保留模糊逻辑。使用辅助工具修改时，自己解释每一处关键变更；不懂的改动回到语法与词典核对。

## 练习

写一段真实项目更新：做了什么、结果是什么、还不清楚什么、下一步是什么。再写一个请求同事协助的邮件主题和两句话。
